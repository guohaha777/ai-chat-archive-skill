目录清楚只是一半，每篇文档内部也要清楚。读者打开一页，应该在十秒内知道这页是什么、自己要的东西在哪一节。

## 哪些固定，哪些跟着内容变

版式规定的是“一页怎么排才好读”，不规定“必须有哪些页、讲什么”。每个人的聊天内容不一样，页面要从他的内容里长出来。

| 固定的（让任何页面都好读、好找） | 跟着内容变的 |
| --- | --- |
| 一页的骨架：标题、引言、定位表、页尾边界 | 一个话题有哪几页、每页叫什么 |
| 按内容的形状选表格、图、代码块 | 每页有哪些小节、小节叫什么 |
| 原文和整理稿分得清 | 知识页怎么划分（按这个话题自己的领域） |
| 页面顺序：总览在前，速查在后 | 第一层类别叫什么、有几个 |
| 文件夹内从 00 连续编号 | 页面类型本身：下面没有合适的就新设计一种 |

下文“各类页面”列的是常见类型，不是全集，也不是每个话题都要凑齐的清单。表里标“必备”的小节，意思是“既然建了这类页面，这一节是它存在的理由”；对应的内容不存在，就不建这类页面。

不同内容的话题，页面组成会很不一样：

| 话题的内容 | 可能的页面组成 |
| --- | --- |
| 软件项目 | 总览、按子系统分的知识页、问题与排查、决策记录、指令与命令、术语表 |
| 写作或创作项目 | 总览、设定与素材、结构与大纲的演变、修改意见与取舍、可复用的提示词、术语与风格词 |
| 学一门知识 | 总览（核心问题和概念地图）、按主题分的概念页、易错点与纠正、练习与例题、术语表 |
| 个人复盘、职业规划 | 总览（反复出现的张力）、被事实纠正的判断、行动依据与待验证的问题 |
| 零散的同领域问答 | 一页速查，必要时加一页术语 |

节点二里用户对样张提出的版式调整，优先于本文件。用户想要另一种排法，就按他的来，并用到其余所有话题。

## 目录和页面组成

```text
<知识库>/
├── 00_知识库入口.md
├── 01_项目/
│   ├── <话题甲>/
│   │   ├── 00_项目总览.md
│   │   ├── 01_……
│   │   └── 07_术语表.md
│   └── <话题乙>/
└── 02_专题知识/
    └── <话题丙>/
```

第一层是类别，第二层一个话题一个文件夹，两者都来自 `topics.json`，不要改名。第三层是页面，文件名 `两位编号_页面名.md`，每个文件夹从 `00` 连续编号。不再往下分层。

一个话题有哪几页，看 `digest/_index.md` 里它的原文规模和精选里实际有什么：

| 话题规模（原文字数） | 页数 | 典型页面 |
| --- | --- | --- |
| 大（五十万字以上的长期项目） | 8 到 11 页 | 总览、过程复盘、两到三个知识页、问题与排查、决策记录、指令与命令、术语表 |
| 中（十万到五十万字） | 4 到 7 页 | 总览、一到两个知识页、排查和决策并成一页、术语与指令速查 |
| 小（十万字以内） | 1 到 3 页 | 一页速查，必要时加一页术语或指令 |

页面顺序固定：`00` 总览在最前；然后是知识页；再是过程复盘、问题与排查、决策记录；指令与命令、术语表这类速查页在最后。

表里的页数是常见范围，不是指标。下限尤其如此：页数由材料决定，材料只够四页就写四页。

某类内容没有，就不建那一页。同一类内容再多也只有一页（指令和命令确实都很多时可以分成两页），多出来的靠筛选解决，不靠拆页。

## 预算：提炼，不搬运

笔记的价值在于比原对话短得多、又能直接用。写得比需要的长，读者就不会回来看。

| 对象 | 预算 | 超了怎么办 |
| --- | --- | --- |
| 一页 | 1500 到 3500 字；术语表、指令与命令页最多 5000 字 | 合并同类项，次要的收进表格的一行 |
| 一个话题 | 最多 12 页、合计 4 万字；大话题通常 2 到 3 万字 | 减页，不是每页都删一点 |
| 问题与排查 | 一张索引表收全部故障，一行一个；单独成节的最多 8 个 | 只给“下次还会遇到、定位过程有启发”的故障单独成节 |
| 决策记录 | 一张索引表；单独成节的最多 8 个 | 没有取舍的选择不算决策，写进知识页的一句话 |
| 指令库 | 每类用途 1 到 2 条原文，全页最多 12 条 | 同一条指令的多次微调只留最后有效的一版，写一句它改了什么 |
| 命令 | 按用途分组，每组最多 6 条 | 同族命令留一条代表加一句“变体：换参数……” |
| 术语表 | 最多 60 个；原文五十万字以上的话题最多 100 个 | 只留本人问过、用错过、或项目里反复出现的词 |

怎样判断一条内容该不该进页面，问三个问题：

1. 半年后遇到同样的事，这条能让我少走弯路吗？
2. 它是这个话题特有的，还是随便一搜就有的常识？
3. 它已经被另一条更概括的说法覆盖了吗？

三个问题答完仍然想留，再留。“建错了目录”“两条命令粘在了一起”这类一次性的操作失误，最多在索引表里占一行。

提炼的方向是往上归纳一层：五个各不相同的 502 故障，读者需要的是“502 先分清请求停在网关、容器还是应用”这一条和一张判断图，而不是五段经过。每个单独成节的案例结尾都要有一句可迁移的**经验**；写不出经验的案例，说明它不值得单独成节。

`verify` 报 `PAGE_TOO_LONG`、`TOO_MANY_PAGES`、`TOPIC_TOO_LONG` 时按上表处理。

## 写薄了，和硬凑的区别

预算防的是写多，但也会写少：一个几十万字的项目只写成四五页概述，反复用过的命令、专门问过的术语、发给 AI 的指令原文都没留下。

判断写薄不看页数，看**有没有具体的材料没处放**。`verify` 报 `MATERIAL_WITHOUT_A_PAGE` 时会点名：哪一类（命令、术语、给 AI 的指令、方法与流程、问题与排查、决策），精选和原文资产里有多少，页面里有多少。处理顺序：

1. 先看点名的那类材料是不是真的值得留。原文里重复三次以上的命令、本人问过并得到解释的术语、实际发出去的指令，通常值得。只是被线索词碰巧命中的，不值得，说明理由后不补。
2. 值得留的，优先补进已有页面的一节。只有一节装不下、或它本来就该是速查页（指令与命令、术语表）时才新建一页。
3. 报告里的 `usual_pages_at_least` 只是同等规模话题的常见页数，用来提醒“可能写薄了”，不是要达到的数字。材料都有了去处，页数比它少也没问题，警告会自己消失。

**不要为了消掉警告或凑够页数而加页。** 硬凑的页面有几个特征，`verify` 会查其中两个：

| 特征 | 怎么办 |
| --- | --- |
| 一页只有几行（`PAGE_TOO_THIN`，少于 500 字） | 并进相邻的页面，当一节 |
| 两页大段内容相同（`PAGES_REPEAT_EACH_OTHER`） | 留一处，另一处用双链指过去 |
| 把一件事拆成“概述”“详情”“补充”几页 | 合成一页 |
| 整节是常识或教程，对话里没有对应内容 | 删掉；笔记只写这段对话里发生过、确认过的事 |
| 表格里塞进“暂无”“待补充”的行，或只有一个决策也建一页决策记录 | 删掉空行；并进知识页 |

每加一页之前问一句：这页的内容是从精选或原文资产里来的吗？读者会专门为了它打开这一页吗？两个都答“是”才加。

根目录下的 `00_跨话题汇总/` 由脚本生成（`kb.py hub`），不手写、不手改。它能收到什么，取决于各话题页面是否守下面三条约定：

| 内容 | 约定 |
| --- | --- |
| 术语 | 放在表格里，表头第一列写“术语”，第二列写含义。不要把术语写成列表或段落 |
| 命令 | 放在标了语言的代码块里（`bash`、`sql`、`powershell`……），代码块前一句说它用来做什么 |
| 给 AI 的指令 | 放在 `text` 代码块里，所在小节的标题带“指令”或“提示词” |

原文资产里命令有十条以上，或给 AI 的指令有五条以上的话题，必须有“指令与命令”页（或分成“命令”“指令库”两页），不要只把命令散在排查页和部署页里：那样既不好查，汇总也分不出用途。

知识库根目录只有一个入口页 `00_知识库入口.md`，任何页面都要能从它两次点击内到达。

## 所有页面共用的规则

每一页都按这个骨架：

```markdown
---
tags: [<话题名>, <页面类型>]
---

# <话题名> <页面名>

> 一两句话：这页是什么，适合什么时候来查。

## 快速定位

| 想查什么 | 去这里 |
| --- | --- |
| …… | [[#小节名]] |

## 第一个小节
……

---

资料边界：一两句话说明内容来自哪段时期的对话，哪些当前状态需要重新确认。
```

- **一个 H1**，写“话题名 + 页面名”，这样搜索结果和标签页都认得出。
- **H1 下面紧跟一句引言**，用引用块。说这页回答什么问题，不说“本页整理自……”。
- **超过四五个小节的页面，开头放一张定位表**，一列写读者想查的事，一列链到小节。短页面不需要。
- **小节标题写读者要查的对象或要问的问题**：“登录成功但用户名不显示”“为什么先用假数据”。不写抽象论断，如“先复现，后修改”。
- **标题最多到三级**。需要第四级时，改用表格或加粗的小标签。
- **一段不超过四五行**。超过了，通常说明它该是列表、表格或两段。
- **案例和故障小节的结尾留一句“经验”**，加粗标出，一句话说以后遇到同类情况该怎么做。
- **术语、命令、指令按约定的版式写**（见上文“目录和页面组成”的三条约定），跨话题汇总才收得到。
- **资料边界集中放在页尾**，一处说清。不要每段都加“据对话记录”“尚未核实”。
- **页面之间用双链**。提到另一页讲的内容时链过去，不复制正文。
- **不出现整理过程的痕迹**：`u12` 这类编号、“精选”“本次整理”“候选”“来源单元”都不进正文。

frontmatter 只放 `tags`，需要时加 `aliases`（项目的别名、英文名），方便搜索。不放空属性。

## 选哪种形式

形式跟着内容的形状走，不是每页都要凑齐表格和图。

| 内容的形状 | 用什么 |
| --- | --- |
| 多个对象在相同维度上比较；一问一答式的速查 | 表格 |
| 有先后的流程、阶段、数据流向 | Mermaid `flowchart LR` |
| 排查时的分支判断（是/否走不同路） | Mermaid `flowchart TD`，节点写判断问题 |
| 能直接复制去用的东西：命令、配置、指令原文 | 代码块，标明语言；自然语言指令用 `text` |
| 当时的原话，尤其是被纠正的说法 | 引用块 |
| 并列的要点、检查项 | 列表 |
| 因果解释、取舍理由 | 短段落 |

Mermaid 的节点文字用双引号包起来，避免中文标点导致渲染失败。一张图不超过十来个节点，放不下就拆成两张。图里的每条箭头都要有原文依据，时间上相邻不等于因果。

## 各类页面

下面每类给出必备的小节和可选的小节。必备的是这类页面存在的理由；可选的有内容才写。

### 总览（`00_`）

读者的问题：这是什么，现在到哪了，我该看哪一页。

| 小节 | 内容 | 形式 |
| --- | --- | --- |
| 一分钟看懂（必备） | 解决什么问题、核心体验、怎样做出来的、最值得复用的经验、当前状态确定吗 | 问题—结论表 |
| 核心机制或闭环（必备） | 这个项目或主题的主线 | 流程图 |
| 阶段（项目类） | 每个阶段做了什么、得到什么 | 表格 |
| 组成（项目类） | 技术层次或内容板块 | 表格 |
| 按问题阅读（必备） | “你想了解……去这里”，链到本话题每一页 | 表格 |
| 仍需重新确认 | 线上状态、外部服务等会过时的事实 | 列表 |

非项目类的话题（学习主题、个人复盘）没有“阶段”和“技术组成”，换成“核心问题”“主要区别”“目前的判断”。

### 知识页

读者的问题：这一块是怎么回事，有哪些要点。

一个话题的知识页按它自己的领域或子系统划分，每页讲一块。小节按对象组织：流程、界面与职责、数据结构、关键原则。每个小节先给结论或关系，再给依据。相关的决策可以用一句话摘要并链到决策页。

结尾可以设“不能从材料得出的结论”，列出读者容易想当然、但对话里其实没有依据的事。

### 过程复盘

读者的问题：这件事是怎么一步步做出来的，哪些做法值得重复。

| 小节 | 内容 | 形式 |
| --- | --- | --- |
| 结论先行（必备） | 三到五条最重要的经验，每条一句加粗的结论加一句解释 | 编号列表 |
| 阶段（必备） | 每阶段要回答的问题和出口 | 流程图加表格 |
| 反复有效的做法 | 被多次验证的规则 | 列表 |
| 代价 | 这套做法的成本和没解决的问题 | 列表 |

这不是按日期排的流水账。时间线只在解释“为什么后来改了”时出现。`原文资产.md` 的流程候选列出了对话里成段的步骤，从中找被实际走过、可以再用的那几套，用 `show` 看全文后归纳成自己的流程，不照抄待办清单。

### 问题与排查

读者的问题：我又遇到这个症状了，上次是怎么定位的。

| 小节 | 内容 | 形式 |
| --- | --- | --- |
| 故障索引（必备） | 症状、定位到的关键边界、处理方向、最小验证 | 一张表，每个故障一行；小故障只出现在这里 |
| 典型故障各一节（最多 8 个） | 标题写症状；排查项、分支判断、处理、验证；结尾一句**经验** | 排查项用表格，分支用流程图 |
| 通用排查顺序 | 多个故障共有的检查顺序 | 流程图或编号列表 |

标题用症状而不是根因，因为读者再次遇到时看到的是症状。区分“当时怀疑过”和“证据确认的”。只有修复建议、没有验证结果的，写明“未见验证”。

### 决策记录

读者的问题：当时为什么这么选，放弃了什么。

| 小节 | 内容 | 形式 |
| --- | --- | --- |
| 决策索引（必备） | 决策、选择、主要理由、代价或后续影响 | 一张表 |
| 重要决策各一节（最多 8 个） | 标题编号加一句话；**问题**、**选择**、**结果** 三个加粗标签各一段 | 短段落 |
| 尚未闭环的决策 | 讨论过但没定、或定了没验证的 | 列表 |

最后出现的方案不自动等于最终决定。原文没有理由的，写“理由未记录”。

### 指令与命令

读者的问题：那条命令怎么写来着；上次是怎么跟 AI 说清楚的。

这页是直接拿来用的，原文的准确性比解释重要。

| 小节 | 内容 | 形式 |
| --- | --- | --- |
| 快速选择（必备） | 需要做什么，去哪一节 | 表格 |
| 命令，按用途分节（有则必备） | 命令原文；一两句说明执行位置和前提；能证明什么、不能证明什么 | 代码块；说明用短段落或表格 |
| 指令写法纠偏（有则必备） | 原来的问题、为什么会被误解、更好的写法方向 | 三列表格 |
| 真实纠偏案例 | 原说法（引用块）、问题、改进后（代码块） | 每个案例一小节 |
| 可复用的指令骨架 | 从多次实践整理出的模板 | 代码块，小节标题或上一行写明是模板 |

**原文和整理稿必须分得清。** 从对话里逐字抄来的命令和指令，直接放代码块。自己归纳的模板、改写后的示例，在小节标题或代码块前一行用“模板”“骨架”“改写”“示意”“整理”这类词说明。`check_vault.py` 会找出既不在原文里、又没有这类说明的代码块。

材料在 `原文资产.md` 里：命令已按工具分组并标了出现次数，出现多的通常是日常要用的；指令已按“像不像指令”排过序。从中挑选，按**用途**重新分组（“更新线上版本”“看日志”），不按工具。同族的命令留一条代表，关键变体用一句话说明。密钥和口令换成尖括号占位符。有破坏性的命令照实保留并写明风险。

指令原文很长时，保留完整的一两条作范例，其余只写“这类指令的要点”表格。命令很多、指令也很多时，拆成“指令库”和“命令”两页，每页仍守预算。

### 术语表

读者的问题：这个词是什么意思，我该用哪个词去描述。

| 小节 | 内容 | 形式 |
| --- | --- | --- |
| 快速定位（分组多于三组时） | 想查哪类词，去哪一组 | 表格 |
| 每个领域一组（必备） | 术语、在这里的含义、用途或典型场景 | 三列表格 |
| 内部词汇 | 项目自己起的名字、字段、组件名 | 单独一组，放最后 |

- 材料先看 `原文资产.md` 的术语候选：本人问过的、有原文解释的优先；界面交互词（hover、tooltip、modal、toast、轮播、弹窗、悬停）单独成一组，不要因为“懂前端的都知道”就略过：本人当时需要用它们指挥 AI；界面按钮名、普通词汇不收。各领域的专有名词（视觉风格、文学手法、心理学概念、技术架构、工作角色）都是这页的正当内容，不只是技术词。
- 术语写原词，中英文都常用时写成“中文（English）”，两种写法都能搜到。
- 含义写它在这个话题里的意思，一句话，不循环定义，不写成百科。
- 不因为“懂的人都知道”就删。对本人来说，当时不懂、问过 AI 的词正是最值得留的。
- 通用术语和项目内部叫法分开，内部叫法不要挤掉可迁移的术语。
- 一个术语一行，不一个术语一页。

### 复盘与原则（个人类话题）

读者的问题：我在哪些事上反复卡住，哪些判断被事实纠正过。

小节按张力或主题组织，每节写：观察到的现象、本人的解释、反例、后来的变化。只用本人明确说过的话，可以改写成第一人称。AI 对本人的评价只能作为“讨论中的一种解释”出现，不写成结论。不从对话推断性格、心理状况或身份。

### 小话题的单页

内容不多的话题，一页写完：引言、要点（表格或列表）、原文资产（代码块）、术语（一张小表）。不拆页，不加定位表。

### 知识库入口（根目录 `00_`）

按类别列出每个话题，每个话题一句话说明，链到它的总览页；话题不多时把各页都列出。最后一小节写“使用边界”：哪些内容会过时、需要使用时重新核实。入口页不讲整理过程。

## 内容不属于以上任何一类时

遇到上面没有的内容（菜谱、旅行攻略、法律条文的理解、乐理、健身计划……），不要硬塞进“问题与排查”或“知识页”，也不要因为没有模板就丢掉。按下面的步骤设计一种新页面：

1. 先写出读者以后会带着什么问题来翻这部分内容，三到五个。
2. 每个问题对应一个小节，标题就用那个问题或要查的对象。
3. 每个小节按“选哪种形式”那张表决定用表格、图、代码块还是列表。
4. 套上共用的骨架：标题、引言、需要时的定位表、页尾边界。
5. 给页面起一个读者一看就懂的名字，按顺序规则编号：讲解类靠前，速查类靠后。

新设计的页面类型在节点二给用户看样张时说明。同一种新类型在多个话题里出现时，排法保持一致。

## 写作时的证据措辞

精选里看得出一件事做到了哪一步，写成正文时用自然的说法体现，不用标签。拿不准某个修复有没有验证时，用 `find` 查一下后文，不要猜：

| 证据状态 | 正文怎么写 |
| --- | --- |
| 已验证 | 直接陈述：“启动时读回未完成的提醒后，重启不再丢失。” |
| 已实施，未见验证 | “当时改成了……，对话里没有记录验证结果。” |
| 只是建议或讨论 | “讨论过的方案是……，没有看到采用的记录。” |
| 被后来推翻 | “起初认为是……，后来日志显示……” |
| 会随时间变化的事实 | 写明时间：“2025 年 3 月时……”，并在页尾边界里提醒重新确认 |

不要给每句话都加限定语。把确定的写确定，把不确定的集中标出，读者才分得清。

正文直接讲知识，不反复写“用户说”“助手建议”。只有当“谁说的”本身影响理解时才写出来，比如一个判断被对方纠正。

## 写完一页后自查

- 只看开头引言和定位表，能不能知道这页有什么？
- 随便挑一节，标题是不是读者会搜的词或会问的问题？
- 有没有超过五行的段落可以改成表格或列表？
- 这页有没有超出预算？有没有哪一节删掉后读者不会觉得少了什么？
- 命令和指令是不是从原文逐字复制、放在代码块里？
- 不是原文的代码块，前面有没有说明它是模板或改写？
- 正文里有没有残留 `u12` 这类编号？
